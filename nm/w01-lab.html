Что вы делаете и зачем

В § 1.8 лекции сформулирована оценка Уилкинсона: наивная сумма из \(n\) слагаемых теряет от полной машинной точности \(u\) до \(nu\). При \(n = 10^7\) это уже \(\sim 10^{-9}\) — далеко не 16 значащих цифр, обещанных binary64. Возникает естественный инженерный вопрос: существует ли алгоритм суммирования, сохраняющий полную машинную точность при любом \(n\)?

Ответ утвердительный. Задача этой лабораторной — реализовать в Python четыре алгоритма суммирования:

  1. Наивный (последовательный цикл слева направо) — рабочая лошадка, чью ошибку мы будем побеждать;
  2. Компенсированный Кэхэна (1965) — суммирование с компенсирующей переменной, восстанавливающей потерянные младшие разряды;
  3. Попарный (тот же, что NumPy применяет в np.sum с версии 1.9) — рекурсивная суммирующая свёртка с ошибкой \(O(u \log_2 n)\);
  4. Отсортированный — сумма слагаемых, отсортированных по возрастанию модуля.

Затем — экспериментально проверить теоретические оценки: построить ошибку каждого алгоритма как функцию \(n\) в двойных логарифмических координатах и убедиться, что она следует закону \(nu\), \(u\), \(u\log n\), \(nu\) соответственно.

Каждый шаг сопровождается автопроверкой в браузере: JS считает эталон в той же арифметике binary64, что и Python, и сверяет введённое вами число. Прогресс сохраняется в браузере (localStorage); по итогу для зачёта нужно решить не менее 10 из 12 задач.

Как работать. Пишете код у себя (Jupyter, IPython, файл — на ваш выбор), запускаете, получаете число, вводите его в поле «ответ». Копировать код из подсказок целиком — можно, но соседняя пара за это оценки не получает: автопроверка проверяет числа, а не факт запуска. Спрашивайте вслух — соседям, преподавателю; лабораторка не «на молчание», а на понимание.

Модель \(\mathrm{fl}(a\circ b) = (a\circ b)(1+\varepsilon)\), \(|\varepsilon|\le u\), гарантирует свойство округления одной операции, но не ассоциативность многих. Во втором порядке \(b+c = -10^{20}+1\) требует представить число \(-10^{20}+1\) в float64, но зазор у \(10^{20}\) равен \(2^{66-52}=16384\), поэтому единица теряется ещё до того, как \(a\) вступит в игру.

§1. Наивная сумма

Определите функцию наивного суммирования — обычный цикл слева направо в арифметике float:

sum_naive.py — скелет
def sum_naive(x):
    """Наивная сумма массива x в float64."""
    s = 0.0
    for xi in x:
        s += float(xi)
    return s

Само число 0.1 уже не представимо точно в двоичной системе: 0.1 = 0x3fb999999999999a / 2^52, ошибка представления \(\approx 5{,}55\cdot 10^{-18}\). §2. Компенсированное суммирование Кэхэна

При добавлении маленького \(x_k\) к большому \(s\) младшие биты \(x_k\) теряются в округлении. Компенсированный алгоритм отслеживает эти потерянные биты в дополнительной переменной \(c\) («компенсация») и вычитает их из следующего слагаемого. Расширенная точность достигается в одинарной точности \(u\).
kahan.py — скелет
def sum_kahan(x):
    """Компенсированное суммирование Кэхэна."""
    s = 0.0
    c = 0.0                # «компенсация» — потерянные младшие разряды
    for xi in x:
        y = float(xi) - c   # возвращаем в игру ранее потерянное
        t = s + y          # обычное сложение — теряет часть y
        c = (t - s) - y    # сколько именно y потерялось
        s = t
    return s
Задача 2.1. Кэхэн на массиве из 0,1. Проверьте, что sum_kahan([0.1]*10**7) даёт погрешность порядка \(u \approx 10^{-16}\), а не \(Nu\). Введите: (а) полученную сумму; (б) абсолютную ошибку.
автопроверка2 поля
В идеале Кэхэн-сумма должна почти точно равняться \(10^{6}\); ошибка ограничена \(2u \cdot \sum|x_k|\) — оценка Кэхэна–Нейманна. Для нашего теста это \(\approx 10^{-10}\) или меньше. Заметьте: компенсация ограничена — она справляется с накоплением, но не спасает от единичной катастрофы (например, при суммировании чисел разных знаков одинакового порядка).
Задача 2.2. Хитрая деталь. Пусть при компиляции с флагом -ffast-math или в оптимизирующем компиляторе преобразование c = (t - s) - y алгебраически упрощается до c = -y + (t - s) и далее до c = 0 (потому что \(t - s = y\)). Что тогда происходит с алгоритмом?
автопроверкавыбор
Компенсированное суммирование живёт исключительно за счёт неассоциативности сложения в машинной арифметике. Если компилятор считает \(+\) и \(-\) ассоциативными и сокращает \((t-s)-y \equiv 0\), защита исчезает. Отсюда правило: критичный численный код собирать без -ffast-math; в Python на CPython проблема неактуальна — интерпретатор ничего не переставляет.

§3. Попарное суммирование

Идея попарного (pairwise) суммирования: сумма пополам делится на две подсуммы, каждая суммируется рекурсивно, потом складывается. Дерево рекурсии имеет глубину \(\log_2 n\), поэтому в худшем случае ошибка ограничена \(u \log_2 n \cdot \sum|x_k|\) — очень медленный рост.

pairwise.py — скелет
def sum_pairwise(x, base=64):
    """Попарное суммирование. base — размер листа, где переключаемся на наивный цикл."""
    x = np.asarray(x, dtype=float)
    n = len(x)
    if n <= base:
        s = 0.0
        for xi in x: s += xi
        return s
    m = n // 2
    return sum_pairwise(x[:m], base) + sum_pairwise(x[m:], base)
Задача 3.1. Попарная сумма на 0,1. Посчитайте sum_pairwise([0.1]*10**7) и введите ошибку. Сравните с наивной суммой из §1.1.
автопроверка1 поле
NumPy применяет попарное суммирование по умолчанию в np.sum начиная с версии 1.9 (см. numpy/_core/src/umath/loops.c.src). Именно поэтому np.sum([0.1]*10**7) в Python даёт гораздо точнее наивной суммы Python-циклом — и это не случайность, а инженерное решение.

§4. Отсортированное суммирование

Ещё одна классическая идея: сортировать слагаемые по возрастанию модуля и суммировать в этом порядке. Тогда каждая частичная сумма относительно велика по сравнению с прибавляемым слагаемым, и вклад «мелочи» в общий итог не теряется в округлении. Практически даёт заметный выигрыш на массивах разного знака и разного порядка.

sorted_sum.py — скелет
def sum_sorted(x):
    """Сумма после сортировки по |x_k| — сначала маленькие."""
    y = sorted(x, key=abs)
    s = 0.0
    for yi in y: s += yi
    return s
Задача 4.1. Смешанные знаки. Возьмите массив \(x_k = (-1)^k / k\), \(k = 1, \ldots, 10^{6}\). Это частичная сумма ряда Лейбница, \(\sum \to -\ln 2 \approx -0{,}693147\ldots\). Посчитайте: (а) sum_naive(x); (б) sum_sorted(x). Введите оба.
автопроверка2 поля
Для убывающего положительного ряда (например, \(1/k^2\)) сортировка по возрастанию — то же самое, что суммирование в обратном порядке. Это спасает от катастрофы «маленького хвоста, поглощённого большой головой». Но при знакопеременных рядах может, наоборот, увеличить катастрофическое вычитание, и тогда лучше работает Кэхэн.

Пришло время построить график и посмотреть, как реально ведёт себя ошибка при росте числа слагаемых. Соберите таблицу для \(n = 10^{3}, 10^{4}, 10^{5}, 10^{6}, 10^{7}\), тест — \([0{,}1]\times n\). Оцените наклон каждой кривой в двойных логарифмических координатах.

for n in ns:

    exact = n * 0.1
    e_naive    = abs(sum_naive(x)    - exact)
    e_kahan    = abs(sum_kahan(x)    - exact)

Задача 5.1. Наклон наивной кривой. На двойном логарифмическом графике зависимость \(\log \varepsilon_{\text{naive}}\) от \(\log n\) — прямая. Определите её наклон \(k\) (эмпирически, между \(n=10^{4}\) и \(n=10^{7}\)) и сверьте с теорией.
автопроверка1 поле
Оценка Уилкинсона (1.9): \(\varepsilon \sim n u\), значит \(\log_{10}\varepsilon \sim \log_{10} n + \log_{10} u\) — прямая с наклоном ровно \(k = 1\). Практически на нашем тесте наклон ближе к \(0{,}5\)-\(0{,}9\) — типичный «стохастический» \(\sqrt n\)-режим (Higham, теорема 4.2), потому что ошибки округления при 0,1 не строго одного знака.
Задача 5.2. Наклон Кэхэна и попарной. На том же графике определите наклоны кривых Кэхэна и попарной суммы. Введите оба.
автопроверка2 поля
Кэхэн — константа: наклон \(\approx 0\). Попарная — очень медленный логарифмический рост \(u\log_2 n\); на нашем диапазоне \(\log_2 n\) меняется всего от 10 до 23 — визуально почти плоская линия. Оба алгоритма кардинально лучше наивного при больших \(n\).

§6. Сходящийся ряд: 1/n²

Классический тест на порядок суммирования — конечная частичная сумма ряда

\[ S_N = \sum_{n=1}^{N} \frac{1}{n^2}, \qquad S_\infty = \frac{\pi^2}{6}. \tag{Л1} \]

Слагаемые убывают. Возникает вопрос: суммировать с начала (сначала большие) или с конца (сначала маленькие)?

Задача 6.1. Прямой и обратный порядок. Возьмите \(N = 10^{7}\), точный эталон посчитайте math.fsum. Посчитайте наивно (а) в порядке \(n = 1, 2, \ldots, N\) и (б) в порядке \(n = N, N-1, \ldots, 1\). Введите обе абсолютные ошибки против fsum.
автопроверка2 поля
Суммирование с конца (сначала маленькие) на порядок точнее. Причина: когда мы прибавляем \(1/N^2 \approx 10^{-14}\) к уже накопленной большой сумме \(\sim 1{,}6\), младшие биты \(1/N^2\) отсекаются на уровне \(u \cdot 1{,}6 \approx 10^{-16}\). Наоборот, при суммировании с конца частичные суммы малы, и в них помещаются младшие разряды всего хвоста ряда.
Задача 6.2. Какой алгоритм побеждает? Посчитайте \(S_{10^{7}}\) четырьмя способами: naive-forward, naive-backward, Kahan, pairwise. Сравните с fsum. Кто оказался ближе всех к fsum?
автопроверкавыбор
Кэхэн должен совпадать с fsum до последнего бита или отставать на 1 младший бит. Попарная — почти совпадать (для убывающих неотрицательных рядов). naive-backward — на 1-2 младших бита хуже Кэхэна, но всё ещё почти идеально. naive-forward — уверенно проигрывает всем.

Что унести с лабы

  1. Наивная сумма из \(n\) слагаемых теряет от \(nu\) до \(\sqrt n\, u\) точности — эмпирически подтверждено.
  2. Компенсированное суммирование Кэхэна возвращает полную машинную точность \(\sim u\) ценой ×4 арифметических операций.
  3. Попарное суммирование даёт \(u\log_2 n\) без вспомогательных переменных — потому оно и стало умолчанием в NumPy.
  4. Порядок слагаемых имеет значение: для рядов с убывающими членами суммируйте с конца.
  5. Не полагайтесь на «математическую» ассоциативность \(+\) в оптимизирующем компиляторе: -ffast-math ломает Кэхэна.
